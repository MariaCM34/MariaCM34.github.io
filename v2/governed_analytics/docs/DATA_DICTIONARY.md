# Data dictionary and lineage

All source records are fictional and generated by `analytics/pipeline.py` with formula seed `formula-v1`. The generator writes UTF-8 JSONL plus `source_manifest.json` with per-file SHA-256 digests. The loader validates records, writes `raw_*` DuckDB tables, and records rejected source IDs and reasons in `rejections.jsonl`. Successful builds replace the warehouse snapshot only after the new build completes.

| Source / business key | Fields and contract | Persisted target |
|---|---|---|
| `products.jsonl` / `product_id` | category one of tools, parts, supplies | `raw_products`, `dim_product` |
| `orders.jsonl` / `order_id` | timezone-aware `placed_at`, status completed/cancelled, currency USD/COP | `raw_orders`, `fct_orders` |
| `order_lines.jsonl` / `line_id` | valid order/product FK, positive quantity, nonnegative integer unit and discount minor units; discount ≤ extended gross | `raw_order_lines`, `fct_order_lines` |
| `returns.jsonl` / `return_id` | valid completed-order line, timezone-aware acceptance time, accepted/rejected status, nonnegative amount; accepted total ≤ discounted line | `raw_returns`, `fct_returns` |

`fct_order_lines` grain is exactly one accepted order line. `gross_minor = quantity × unit_minor`; `sales_minor = gross_minor − discount_minor`; it joins stable product category and the order's currency/status/time. `fct_returns` grain is exactly one return event and carries its line/order/category/currency through an FK join. It is **not joined to line facts in the aggregate query**: each fact is aggregated separately, then the groups are combined. `fct_orders` grain is one eligible placed order, so a three-line order has one cancellation denominator record. All timestamps are normalized to UTC before storage. DuckDB `TIMESTAMP` columns are UTC-naive by explicit convention; API date filters and `strftime` use UTC.

The source and model are related by stable IDs (`line_id`, `order_id`, `product_id`, `return_id`). The API response provides source snapshot hash, semantic version, exact SQL and parameters. A specific row can be traced with a read-only DuckDB query such as:

```sql
SELECT r.return_id, r.line_id, r.order_id, r.event_at, r.amount_minor,
       l.product_id, l.category, l.sales_minor
FROM fct_returns r JOIN fct_order_lines l USING (line_id)
WHERE r.return_id = 'R000007';
```

`parquet/<run_id>/` contains copies of `dim_product`, `fct_orders`, `fct_order_lines`, and `fct_returns` for inspection or reuse. They are derivatives, not additional independent source events. `run_manifest` records the published run ID, model version/hash, aggregate source checksum/count, rejected count and process time. Only the generation matching that `run_id` belongs to the current warehouse.
